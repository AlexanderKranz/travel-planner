# Runbook

Click-by-click procedures for running Travel Planner. Provider facts were checked on 2026-10-27:
- Vercel Instant Rollback: https://vercel.com/docs/instant-rollback
- Supabase CLI in CI: https://supabase.com/docs/guides/deployment/managing-environments
- Supabase backup/restore and connection strings: https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore and https://supabase.com/docs/guides/database/connecting-to-postgres
- GitHub artifacts API: https://docs.github.com/en/rest/actions/artifacts

Secrets are referred to by **name** only. Never paste a secret value into the repo, an issue, a chat or a log.

## 1. How a change reaches production

1. Work happens on a branch. Open a **pull request** on GitHub.
2. Vercel builds a **preview** automatically; the link appears as a comment on the PR. Click it and try the change. Preview uses the Preview env vars.
3. The **CI** check (lint, typecheck, tests, build) must be green.
4. Click **Merge pull request**. Vercel deploys `main` to production within a minute or two (Vercel -> project -> Deployments).
5. If the PR changed `supabase/migrations/**`, the GitHub Action **Deploy database migrations** (`deploy-db.yml`) also runs and applies the new SQL to the production database. Check it: GitHub -> Actions tab -> "Deploy database migrations" -> green check.

Important: the app and the database deploy independently and in parallel. Write migrations so the old app version still works with the new schema (add columns/tables first, remove things only in a later release).

Run the migration by hand: Actions -> Deploy database migrations -> **Run workflow** -> branch `main`.

## 2. Rollback

### App (Vercel) - one click
1. Vercel -> your project -> **Overview**. On the Production Deployment tile click **Instant Rollback**.
2. Pick the previous deployment (on the Hobby plan only the immediately previous one is offered), click **Continue**, check the domain list, click **Confirm Rollback**.
3. Effect is immediate. Vercel now **stops auto-deploying new pushes** to production. When the fix is merged, click **Undo Rollback** on the same tile and promote the new deployment to resume normal behaviour.
4. Environment variables are not rolled back, only code.

### Database - there is no "undo"
Migrations only go forward. If a migration broke something:
1. Preferred: write a **new migration** that fixes it (new PR, merge, `deploy-db.yml` applies it).
2. If data was damaged or lost: restore from backup (section 5) into a **new scratch project**, then copy back what you need, or - last resort, full disaster recovery - restore into production with `--allow-prod`.

## 3. GitHub secrets (one-time setup)

GitHub -> repository **Settings** -> **Secrets and variables** -> **Actions** -> **New repository secret**. Create these two (Name exactly as written). Both workflows use only these; no Supabase access token is needed:

| Name | Where to find the value |
|---|---|
| `SUPABASE_DB_URL` | Click **Connect** at the top of the project -> **Connection string** -> tab **Session pooler** -> copy the URI (looks like `postgresql://postgres.<ref>:[YOUR-PASSWORD]@aws-0-<region>.pooler.supabase.com:5432/postgres`) and replace `[YOUR-PASSWORD]` with the real password. If the password has special characters (`@ : / ? # %`), percent-encode them. **Use the session pooler, not "Direct connection"**: GitHub's runners only speak IPv4, and Supabase Free direct connections are IPv6 only. |
| `BACKUP_PASSPHRASE` | Make one up: at least 6 random words or 30+ characters, e.g. generated by your password manager. |

**Do this now for `BACKUP_PASSPHRASE`:** save the same passphrase in your password manager as "Travel Planner backup passphrase" *before* pasting it into GitHub. GitHub never shows a secret again. **Without the passphrase every backup is unreadable.** Also keep a copy outside the NAS (the NAS holds the encrypted backups; a second copy of the passphrase on paper in a safe place is reasonable).

Test: Actions -> **Nightly database backup** -> **Run workflow**. It should turn green in a few minutes and show an artifact `db-backup-<timestamp>` at the bottom of the run page. Then run **Deploy database migrations** manually once (it only says "Remote database is up to date" while there are no migrations).

Notes:
- Free plan connection limits: Supabase documents session-pooler limits on its pooling guide (not verified here). One backup and one migration run at a time uses only a couple of connections, which is fine; the workflows are serialised with `concurrency`.
- GitHub pauses scheduled workflows in a repository with no activity for 60 days. Check the Actions tab now and then; re-enable with one click if paused.
- If a nightly backup fails, GitHub emails you (Settings -> Notifications -> Actions: "Send notifications for failed workflows only").

## 4. Pull backups to the DiskStation (DSM)

The Actions artifact lives only 30 days. The NAS script keeps 30 daily + 12 monthly copies.

### 4a. Create a read-only GitHub token
GitHub -> your avatar -> **Settings** -> **Developer settings** -> **Personal access tokens** -> **Fine-grained tokens** -> **Generate new token**:
- Name `nas-backup-pull`, expiration 1 year (put a reminder in your calendar), Resource owner: you.
- Repository access: **Only select repositories** -> `travel-planner`.
- Permissions -> Repository permissions -> **Actions: Read-only**. Nothing else.
- Generate and copy the token (`github_pat_...`).

### 4b. Put script and config on the NAS
1. Copy `scripts/backup/pull-to-nas.sh` to the NAS, e.g. `/volume1/scripts/travel-planner/pull-to-nas.sh` (File Station upload, or `scp`). Make it executable: `chmod +x pull-to-nas.sh`.
2. Create the config file outside any shared repo, with the NAS user that will run the task (via SSH, enable SSH in Control Panel -> Terminal & SNMP):
   ```
   mkdir -p ~/.config
   vi ~/.config/travel-planner-backup.env
   ```
   Content (use your values):
   ```
   GITHUB_TOKEN=github_pat_xxxxxxxx
   GITHUB_REPO=AlexanderKranz/travel-planner
   BACKUP_DIR=/volume1/backups/travel-planner
   ```
   Then `chmod 600 ~/.config/travel-planner-backup.env` (the script refuses a config others can read).
3. Test once by hand: `sh /volume1/scripts/travel-planner/pull-to-nas.sh --help`, then run it without `--help`. You should see `saved .../daily/...zip`. Running it again says "already downloaded, nothing to do".

### 4c. Schedule it
DSM -> **Control Panel** -> **Task Scheduler** -> **Create** -> **Scheduled Task** -> **User-defined script**:
- General: name `Travel Planner backup pull`, User: the user who owns the config file.
- Schedule: Daily, at 06:00 (the backup runs about 02:00-03:00 Berlin).
- Task Settings: Run command `sh /volume1/scripts/travel-planner/pull-to-nas.sh`; tick "Send run details by email" (and "only when the script terminates abnormally") so errors reach you.
- OK, then select the task and **Run** once to test.

Optionally add `/volume1/backups/travel-planner` to your existing Hyper Backup job.

The script needs `curl`; `unzip` is used for an integrity test when present (the script prints a note when not). It does not need `jq`.

## 5. Restore

Backups are the `.zip` stored on the NAS (it contains `db-backup-<timestamp>.tar.gz.gpg`). Inside:
- `data.sql`: data of the schemas `public` and `auth` (this is what gets restored).
- `schema.sql`: full schema incl. `private`, `extensions`, the trigger on `auth.users`. **Reference only**, it is never replayed.
- `MANIFEST.txt`: `git_commit` (commit of `main` at backup time) and `migration_version` (latest applied migration).

Why: the structure of a database comes from the migrations in `supabase/migrations/`, not from the dump. So a restore is "new project -> apply the migrations of that commit -> load the data".

Restore always goes into a database **you name**. Never into production unless production is lost. `restore.sh` refuses a target whose migration version differs from the MANIFEST.

1. **Tools (once).** `brew install gnupg libpq unzip supabase/tap/supabase`, add `libpq` to PATH (`brew link --force libpq`). `psql` major version must be >= the server's.
2. **Read the MANIFEST.** Simply start `restore.sh` (step 5) without having done step 4: it prints the MANIFEST before it checks anything and stops on a mismatch. Note `git_commit` and `migration_version`.
3. **New Supabase project.** https://supabase.com/dashboard -> **New project**, region Frankfurt, choose and save a database password. Leave it empty. Note its Reference ID (Project Settings -> General) and its session pooler string (**Connect** -> Session pooler, as in section 3).
4. **Apply the migrations of that commit.** In the repo on your Mac:
   ```
   git checkout <git_commit from MANIFEST>
   supabase login
   supabase link --project-ref <NEW_REF>
   supabase db push
   git checkout -    # back to your branch afterwards
   ```
   `db push` asks for the new database password. It must end without errors; this creates `private`, the functions, policies and the `auth.users` trigger.
5. **Load the data.** (`--prod-host` is the production project ref, e.g. the first part of `https://<ref>.supabase.co`.)
   ```
   export BACKUP_PASSPHRASE='...'   # or omit; gpg will ask. A leading space keeps it out of shell history
   scripts/backup/restore.sh \
     --file ~/Downloads/20261027T010009Z__300__db-backup-20261027T010000Z.zip \
     --target 'postgresql://postgres.NEWREF:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres' \
     --prod-host PRODREF
   ```
   It prints the MANIFEST, checks the migration version (before anything else is asked), asks you to type the target host, then loads `data.sql` in one transaction with triggers off. On any error nothing is changed. A version mismatch stops it with the exact `git checkout`/`db push` hint; `--skip-version-check` overrides that (e.g. old backups without `migration_version`; only if you understand why).
6. **Re-apply Auth settings.** They live in the Dashboard, not in the database, so they are **not in the backup**: Authentication -> URL configuration, providers, email templates, **SMTP**, and the **Before User Created hook** (Authentication -> Hooks). Follow `docs/specs/phase-1-dashboard-steps.md` step by step.
7. **Verify row counts.** SQL Editor in the old (if still reachable) and new project: `select count(*) from auth.users;` and `select count(*) from public.trips;` (and other main tables). Equal, or production slightly higher.
8. **Switch over (real disaster only).** Update Vercel env vars `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, and GitHub secret `SUPABASE_DB_URL`; redeploy (Deployments -> latest -> Redeploy).

Important: **all users have to log in again** (the new project has a different JWT secret; sessions are not carried over). Password hashes are restored, so passwords keep working.

`--allow-prod` allows restoring into the *existing* production project; last resort only.

Known caveats: custom roles' passwords are not in a backup; Storage files are not backed up (the app stores none); `auth.schema_migrations` and `supabase_migrations` are deliberately not restored (the new project writes its own). Later improvement (TODO in `backup.yml`): write the backup result to `public.app_events`; needs the Supabase secret key as a GitHub secret.

### Quarterly restore test (put it in your calendar: Jan/Apr/Jul/Oct)
1. Pull the newest backup from the NAS (or download the artifact from the Actions run page).
2. Restore it into a scratch project as above (steps 3 to 5, 7).
3. Compare row counts. In the SQL Editor of both projects run `select count(*) from auth.users;` and the same for the main tables (for example `select count(*) from public.trips;`). Production counts should be equal or slightly higher (new data since last night).
4. Delete the scratch project. Note the date and result somewhere; a backup never restored is only a hope.

## 6. Rotating a leaked or old key

General rule: create the new key, deploy it, then revoke the old one.

| Key | Steps |
|---|---|
| Supabase secret key (`SUPABASE_SECRET_KEY`) | Supabase -> Project Settings -> API Keys -> create a new secret key; update it in Vercel (Settings -> Environment Variables, Production and Preview); Deployments -> latest -> **Redeploy**; then delete the old key in Supabase. |
| Supabase DB password | Project Settings -> Database -> Reset database password; update the GitHub secret `SUPABASE_DB_URL` (it contains the password); run both workflows manually to confirm. |
| GitHub NAS token | GitHub -> Developer settings -> Fine-grained tokens: regenerate/delete; update `GITHUB_TOKEN` in the NAS config file. |
| `BACKUP_PASSPHRASE` | New backups use the new passphrase; **old backups still need the old one**. Add the new one to the password manager as a new entry; keep the old entry until the last old backup has aged out (12 months). Update the GitHub secret. |
| Anthropic / AeroDataBox / other API keys | Create new key at the provider, update in Vercel, redeploy, delete the old key. Check the provider's usage page for abuse. |

If a secret was committed to git: rotate it first (the old value is burned, even after deleting the commit), then clean up the repo.

## 7. When UptimeRobot alerts

(`/api/health` is the monitored URL; setup of the monitor itself is described in `docs/hosting-setup.md`.)

1. Open the site yourself. Is it really down, or just the monitor (one alert that clears within a few minutes is usually a blip)?
2. Open `https://<your-domain>/api/health` in a browser. It shows which part is failing, if the route reports checks.
3. Vercel -> project -> **Deployments**: was there a deploy shortly before the alert? If yes -> **Instant Rollback** (section 2). Also check Vercel -> Logs for errors.
4. Supabase dashboard: is the project **Paused**? Free projects pause after about a week of inactivity -> click **Restore project**. Also check https://status.supabase.com and https://www.vercel-status.com.
5. GitHub Actions: did the last "Deploy database migrations" fail half-way? Look at its log.
6. If a database problem looks like data loss: stop changing things and go to section 5.
7. After recovery, write down what happened and why (a few lines are enough).

## 8. Sentry (error tracking)

Sentry collects crashes from the browser and the server and emails you. Docs checked 2026-10-28: https://docs.sentry.io/platforms/javascript/guides/nextjs/manual-setup/ and https://docs.sentry.io/platforms/javascript/guides/nextjs/configuration/build/. Setup steps are in `docs/hosting-setup.md` section 6b.

**What it does and does not do**
- Switched on only when `NEXT_PUBLIC_SENTRY_DSN` is set. Without it the app runs normally and sends nothing.
- Environment = `VERCEL_ENV` (`production` / `preview`, else `development`); release = `VERCEL_GIT_COMMIT_SHA`, so every error shows which deploy caused it.
- Privacy: no session replay, no profiling, no performance tracing (`tracesSampleRate` 0), `sendDefaultPii` off. Before sending, `src/lib/sentry-scrub.ts` removes email addresses, tokens (`token_hash`, `code`, `access_token`, `password`, `apikey`, `Authorization`, cookies) from messages, URLs, query strings, breadcrumbs and request data. At most the Supabase user id is attached (we do not set one at all today). Use an EU-region organisation (de.sentry.io) so the data stays in the EU.
- Handled errors that our code writes with `logEvent()` (table `app_events`) are not sent to Sentry; Sentry only sees unhandled errors. So nothing is reported twice. Do not add Sentry's `captureConsole` integration.
- Source maps (readable stack traces) are uploaded during the Vercel build only if `SENTRY_AUTH_TOKEN` is set, and deleted from the build output afterwards, so they are never public.
- No tunnel route (ad-blocker workaround): a few blocked browsers would not report errors, which is acceptable for a family app, and the tunnel would add a route that needs excluding from the middleware and uses function invocations. If it ever matters, add `tunnelRoute: "/api/monitoring"` to `withSentryConfig` in `next.config.ts` (`/api` is already excluded from the middleware matcher).

**Test that it works**
1. Vercel -> Settings -> Environment Variables: add `SENTRY_TEST_ENABLED` = `true` (Preview only is safest), redeploy.
2. Open `https://<preview-url>/api/debug/sentry-test`. You get a 500 error page; that is intended.
3. In Sentry -> Issues, the error "Sentry test error (intentional...)" appears within a minute, with environment and release set and readable file names/lines (if source maps are configured).
4. Delete `SENTRY_TEST_ENABLED` again and redeploy. Without it the URL returns 404.

**When a Sentry alert email arrives**
1. Open the issue: check environment, release (commit), and how many users/events.
2. If it started with the latest deploy and is serious -> Instant Rollback (section 2).
3. Otherwise fix on a branch; mark the issue "Resolved in next release".
4. If an issue contains an email or token that the scrubber missed: delete the event in Sentry (Issue -> Delete), then extend `src/lib/sentry-scrub.ts` and its test.

**Rotating `SENTRY_AUTH_TOKEN`:** Sentry -> Settings -> Developer Settings -> Organization Tokens: create a new token, update it in Vercel, redeploy, then revoke the old one.

### AeroDataBox quota

Basic plan: 400 units/month (routes 6, FIDS 2, flight dates 2). Every call is logged in `api_calls` (provider `aerodatabox`, column `units`, including charged failures: HTTP errors, schema-invalid 200s and timeouts at nominal cost). Check usage with `select sum(units) from api_calls where provider='aerodatabox' and created_at >= date_trunc('month', now())` (and per day with `date_trunc('day', ...)`).

The guard (`src/lib/server/flights-quota.ts`) reads those sums before each call. Knobs: `AERODATABOX_DAILY_UNITS` (daily cap) and `AERODATABOX_MIN_REMAINING` (monthly margin kept free, default 40).

Accepted risk: there are no reservations, so parallel instances can each pass the check and overshoot the daily cap by a few calls. The monthly margin of 40 units absorbs this. Raise `AERODATABOX_MIN_REMAINING` if it ever bites.
