# Runbook

Click-by-click procedures for running Travel Planner. Provider facts were checked on 2026-10-27:
- Vercel Instant Rollback: https://vercel.com/docs/instant-rollback
- Supabase CLI in CI: https://supabase.com/docs/guides/deployment/managing-environments
- Supabase backup/restore and connection strings: https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore and https://supabase.com/docs/guides/database/connecting-to-postgres
- GitHub artifacts API: https://docs.github.com/en/rest/actions/artifacts

Secrets are referred to by **name** only. Never paste a secret value into the repo, an issue, a chat or a log.

## 1. How a change reaches production

1. Work happens on a branch. Open a **pull request** on GitHub.
2. Vercel builds a **preview** automatically; the link appears as a comment on the PR. Click it and try the change. Preview uses the Preview env vars.
3. The **CI** check (lint, typecheck, tests, build) must be green.
4. Click **Merge pull request**. Vercel deploys `main` to production within a minute or two (Vercel -> project -> Deployments).
5. If the PR changed `supabase/migrations/**`, the GitHub Action **Deploy database migrations** (`deploy-db.yml`) also runs and applies the new SQL to the production database. Check it: GitHub -> Actions tab -> "Deploy database migrations" -> green check.

Important: the app and the database deploy independently and in parallel. Write migrations so the old app version still works with the new schema (add columns/tables first, remove things only in a later release).

Run the migration by hand: Actions -> Deploy database migrations -> **Run workflow** -> branch `main`.

## 2. Rollback

### App (Vercel) - one click
1. Vercel -> your project -> **Overview**. On the Production Deployment tile click **Instant Rollback**.
2. Pick the previous deployment (on the Hobby plan only the immediately previous one is offered), click **Continue**, check the domain list, click **Confirm Rollback**.
3. Effect is immediate. Vercel now **stops auto-deploying new pushes** to production. When the fix is merged, click **Undo Rollback** on the same tile and promote the new deployment to resume normal behaviour.
4. Environment variables are not rolled back, only code.

### Database - there is no "undo"
Migrations only go forward. If a migration broke something:
1. Preferred: write a **new migration** that fixes it (new PR, merge, `deploy-db.yml` applies it).
2. If data was damaged or lost: restore from backup (section 5) into a **new scratch project**, then copy back what you need, or - last resort, full disaster recovery - restore into production with `--allow-prod`.

## 3. GitHub secrets (one-time setup)

GitHub -> repository **Settings** -> **Secrets and variables** -> **Actions** -> **New repository secret**. Create these two (Name exactly as written). Both workflows use only these; no Supabase access token is needed:

| Name | Where to find the value |
|---|---|
| `SUPABASE_DB_URL` | Click **Connect** at the top of the project -> **Connection string** -> tab **Session pooler** -> copy the URI (looks like `postgresql://postgres.<ref>:[YOUR-PASSWORD]@aws-0-<region>.pooler.supabase.com:5432/postgres`) and replace `[YOUR-PASSWORD]` with the real password. If the password has special characters (`@ : / ? # %`), percent-encode them. **Use the session pooler, not "Direct connection"**: GitHub's runners only speak IPv4, and Supabase Free direct connections are IPv6 only. |
| `BACKUP_PASSPHRASE` | Make one up: at least 6 random words or 30+ characters, e.g. generated by your password manager. |

**Do this now for `BACKUP_PASSPHRASE`:** save the same passphrase in your password manager as "Travel Planner backup passphrase" *before* pasting it into GitHub. GitHub never shows a secret again. **Without the passphrase every backup is unreadable.** Also keep a copy outside the NAS (the NAS holds the encrypted backups; a second copy of the passphrase on paper in a safe place is reasonable).

Test: Actions -> **Nightly database backup** -> **Run workflow**. It should turn green in a few minutes and show an artifact `db-backup-<timestamp>` at the bottom of the run page. Then run **Deploy database migrations** manually once (it only says "Remote database is up to date" while there are no migrations).

Notes:
- Free plan connection limits: Supabase documents session-pooler limits on its pooling guide (not verified here). One backup and one migration run at a time uses only a couple of connections, which is fine; the workflows are serialised with `concurrency`.
- GitHub pauses scheduled workflows in a repository with no activity for 60 days. Check the Actions tab now and then; re-enable with one click if paused.
- If a nightly backup fails, GitHub emails you (Settings -> Notifications -> Actions: "Send notifications for failed workflows only").

## 4. Pull backups to the DiskStation (DSM)

The Actions artifact lives only 30 days. The NAS script keeps 30 daily + 12 monthly copies.

### 4a. Create a read-only GitHub token
GitHub -> your avatar -> **Settings** -> **Developer settings** -> **Personal access tokens** -> **Fine-grained tokens** -> **Generate new token**:
- Name `nas-backup-pull`, expiration 1 year (put a reminder in your calendar), Resource owner: you.
- Repository access: **Only select repositories** -> `travel-planner`.
- Permissions -> Repository permissions -> **Actions: Read-only**. Nothing else.
- Generate and copy the token (`github_pat_...`).

### 4b. Put script and config on the NAS
1. Copy `scripts/backup/pull-to-nas.sh` to the NAS, e.g. `/volume1/scripts/travel-planner/pull-to-nas.sh` (File Station upload, or `scp`). Make it executable: `chmod +x pull-to-nas.sh`.
2. Create the config file outside any shared repo, with the NAS user that will run the task (via SSH, enable SSH in Control Panel -> Terminal & SNMP):
   ```
   mkdir -p ~/.config
   vi ~/.config/travel-planner-backup.env
   ```
   Content (use your values):
   ```
   GITHUB_TOKEN=github_pat_xxxxxxxx
   GITHUB_REPO=AlexanderKranz/travel-planner
   BACKUP_DIR=/volume1/backups/travel-planner
   ```
   Then `chmod 600 ~/.config/travel-planner-backup.env` (the script refuses a config others can read).
3. Test once by hand: `sh /volume1/scripts/travel-planner/pull-to-nas.sh --help`, then run it without `--help`. You should see `saved .../daily/...zip`. Running it again says "already downloaded, nothing to do".

### 4c. Schedule it
DSM -> **Control Panel** -> **Task Scheduler** -> **Create** -> **Scheduled Task** -> **User-defined script**:
- General: name `Travel Planner backup pull`, User: the user who owns the config file.
- Schedule: Daily, at 06:00 (the backup runs about 02:00-03:00 Berlin).
- Task Settings: Run command `sh /volume1/scripts/travel-planner/pull-to-nas.sh`; tick "Send run details by email" (and "only when the script terminates abnormally") so errors reach you.
- OK, then select the task and **Run** once to test.

Optionally add `/volume1/backups/travel-planner` to your existing Hyper Backup job.

The script needs `curl`; `unzip` is used for an integrity test when present (the script prints a note when not). It does not need `jq`.

## 5. Restore

Backups are the `.zip` stored on the NAS (it contains `db-backup-<timestamp>.tar.gz.gpg`). Inside:
- `data.sql`: data of the schemas `public` and `auth` (this is what gets restored).
- `schema.sql`: full schema incl. `private`, `extensions`, the trigger on `auth.users`. **Reference only**, it is never replayed.
- `MANIFEST.txt`: `git_commit` (commit of `main` at backup time) and `migration_version` (latest applied migration).

Why: the structure of a database comes from the migrations in `supabase/migrations/`, not from the dump. So a restore is "new project -> apply the migrations of that commit -> load the data".

Restore always goes into a database **you name**. Never into production unless production is lost. `restore.sh` refuses a target whose migration version differs from the MANIFEST.

1. **Tools (once).** `brew install gnupg libpq unzip supabase/tap/supabase`, add `libpq` to PATH (`brew link --force libpq`). `psql` major version must be >= the server's.
2. **Read the MANIFEST.** Simply start `restore.sh` (step 5) without having done step 4: it prints the MANIFEST before it checks anything and stops on a mismatch. Note `git_commit` and `migration_version`.
3. **New Supabase project.** https://supabase.com/dashboard -> **New project**, region Frankfurt, choose and save a database password. Leave it empty. Note its Reference ID (Project Settings -> General) and its session pooler string (**Connect** -> Session pooler, as in section 3).
4. **Apply the migrations of that commit.** In the repo on your Mac:
   ```
   git checkout <git_commit from MANIFEST>
   supabase login
   supabase link --project-ref <NEW_REF>
   supabase db push
   git checkout -    # back to your branch afterwards
   ```
   `db push` asks for the new database password. It must end without errors; this creates `private`, the functions, policies and the `auth.users` trigger.
5. **Load the data.** (`--prod-host` is the production project ref, e.g. the first part of `https://<ref>.supabase.co`.)
   ```
   export BACKUP_PASSPHRASE='...'   # or omit; gpg will ask. A leading space keeps it out of shell history
   scripts/backup/restore.sh \
     --file ~/Downloads/20261027T010009Z__300__db-backup-20261027T010000Z.zip \
     --target 'postgresql://postgres.NEWREF:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres' \
     --prod-host PRODREF
   ```
   It prints the MANIFEST, checks the migration version (before anything else is asked), asks you to type the target host, then loads `data.sql` in one transaction with triggers off. On any error nothing is changed. A version mismatch stops it with the exact `git checkout`/`db push` hint; `--skip-version-check` overrides that (e.g. old backups without `migration_version`; only if you understand why).
6. **Re-apply Auth settings.** They live in the Dashboard, not in the database, so they are **not in the backup**: Authentication -> URL configuration, providers, email templates, **SMTP**, and the **Before User Created hook** (Authentication -> Hooks). Follow `docs/specs/phase-1-dashboard-steps.md` step by step.
7. **Verify row counts.** SQL Editor in the old (if still reachable) and new project: `select count(*) from auth.users;` and `select count(*) from public.trips;` (and other main tables). Equal, or production slightly higher.
8. **Switch over (real disaster only).** Update Vercel env vars `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, and GitHub secret `SUPABASE_DB_URL`; redeploy (Deployments -> latest -> Redeploy).

Important: **all users have to log in again** (the new project has a different JWT secret; sessions are not carried over). Password hashes are restored, so passwords keep working.

`--allow-prod` allows restoring into the *existing* production project; last resort only.

Known caveats: custom roles' passwords are not in a backup; Storage files are not backed up (the app stores none); `auth.schema_migrations` and `supabase_migrations` are deliberately not restored (the new project writes its own). Later improvement (TODO in `backup.yml`): write the backup result to `public.app_events`; needs the Supabase secret key as a GitHub secret.

### Restore test (automated; do this quarterly: Jan/Apr/Jul/Oct)

A backup that was never restored is only a hope. The workflow **Restore test** (`.github/workflows/restore-test.yml`) restores the newest nightly backup into a throwaway database on a GitHub runner and checks it. It never connects to the production database (it has no database secret; the script refuses non-local targets). Spec: `docs/specs/phase-6-restore-test.md`.

**Last tested: not yet (update this line after each run: date, backup artifact name, PASS/FAIL).**

How to run it:
1. GitHub -> **Actions** -> **Restore test** -> **Run workflow** (branch `main`; leave "Backup artifact" empty for the newest, or enter a name like `db-backup-20261027T010009Z`) -> **Run workflow**.
2. Wait about 5 to 10 minutes and open the run. Only the job **restore-test** is the real test (the job **dry-run** is the pipeline self-test with fake data and also runs on pushes).
3. Open the run's **Summary** tab. Success looks like: "Result: PASS", a table with every table's row count in the backup and after the restore (all `yes`), and PASS lines for: backup decrypted, restore loaded, migrations equal, row counts complete, `auth.users`/`public.profiles`/`public.trips` have rows, RLS enabled on all public tables, foreign keys without orphan rows.
4. Write the date and result into the "Last tested" line above.

The logs and summary contain counts and table names only, never row content. If you ever see personal data in a log, delete the run (run page -> "..." -> Delete workflow run) and tell the developer.

If it fails (the failing line says which check):
| Message | Meaning and what to do |
|---|---|
| `GitHub secret BACKUP_PASSPHRASE is missing` | Create the secret (section 3). |
| `No non-expired db-backup-* artifact found` | No backup in the last 30 days. Run **Nightly database backup** by hand; look at why it fails. |
| `decryption failed` | The secret `BACKUP_PASSPHRASE` is not the passphrase the backup was made with (for example it was changed after that backup). Try an older artifact via the input, compare with the password manager. **This is serious: until a backup decrypts, you have no usable backup.** |
| `Backup commit ... is not in the repository history` | The commit in the MANIFEST was removed (force push). Restore manually (section 5) using the schema of a nearby commit. |
| `migrations differ` / `migration mismatch` | The throwaway database did not get the migrations of the backup's commit. Look at the "Start throwaway Supabase" step. |
| `row counts: N tables differ` | The restore lost or changed rows. Compare the table in the Summary to find the table. Do not trust the backup; run the nightly backup again and re-test. |
| `RLS is NOT enabled on: <tables>` | Not a backup problem: a table in production has no Row-Level Security. Fix with a new migration (`alter table ... enable row level security` plus policies). |
| `foreign keys: ... FK violation` | The data contains rows pointing at missing parents (names of the constraints are listed). Investigate in production (read-only) before relying on the backup. |
| `restore.sh failed` | The load itself failed and was rolled back. Details are hidden on purpose (they can quote data). Re-run locally (below) to see the full error on your own machine. |

Run it on your own machine (for debugging; you need Docker, `brew install supabase/tap/supabase gnupg libpq`):
```
supabase start                      # empty local database with all migrations (check out the backup's commit first if it is old)
export BACKUP_PASSPHRASE='...'      # leading space keeps it out of shell history
scripts/backup/restore-test.sh --file ~/Downloads/<backup>.zip \
  --target 'postgresql://postgres:postgres@127.0.0.1:54322/postgres'
supabase stop --no-backup
```
Without a backup file you can try the whole pipeline with fake data: create a throwaway passphrase file, `scripts/backup/synthetic-backup.sh --source <same local URL> --out /tmp/x.gpg --passphrase-file <file>`, then run `restore-test.sh` on `/tmp/x.gpg` (the source database must be empty; the script empties it again afterwards).

Optional monthly schedule (off by default, decision D3 in the spec): in `restore-test.yml` remove the `#` in front of the `schedule:` block. It decrypts production backups on a GitHub runner without you watching, so it is your call.

The older manual way (restore into a scratch Supabase project, steps 3 to 5 and 7 of the section above) still works and is the right drill for a real disaster; the automated test is the quick routine check.

## 6. Rotating a leaked or old key

General rule: create the new key, deploy it, then revoke the old one.

| Key | Steps |
|---|---|
| Supabase secret key (`SUPABASE_SECRET_KEY`) | Supabase -> Project Settings -> API Keys -> create a new secret key; update it in Vercel (Settings -> Environment Variables, Production and Preview); Deployments -> latest -> **Redeploy**; then delete the old key in Supabase. |
| Supabase DB password | Project Settings -> Database -> Reset database password; update the GitHub secret `SUPABASE_DB_URL` (it contains the password); run both workflows manually to confirm. |
| GitHub NAS token | GitHub -> Developer settings -> Fine-grained tokens: regenerate/delete; update `GITHUB_TOKEN` in the NAS config file. |
| `BACKUP_PASSPHRASE` | New backups use the new passphrase; **old backups still need the old one**. Add the new one to the password manager as a new entry; keep the old entry until the last old backup has aged out (12 months). Update the GitHub secret. |
| Anthropic / AeroDataBox / other API keys | Create new key at the provider, update in Vercel, redeploy, delete the old key. Check the provider's usage page for abuse. |

If a secret was committed to git: rotate it first (the old value is burned, even after deleting the commit), then clean up the repo.

## 7. When UptimeRobot alerts

(`/api/health` is the monitored URL; setup of the monitor itself is described in `docs/hosting-setup.md`.)

1. Open the site yourself. Is it really down, or just the monitor (one alert that clears within a few minutes is usually a blip)?
2. Open `https://<your-domain>/api/health` in a browser. It shows which part is failing, if the route reports checks.
3. Vercel -> project -> **Deployments**: was there a deploy shortly before the alert? If yes -> **Instant Rollback** (section 2). Also check Vercel -> Logs for errors.
4. Supabase dashboard: is the project **Paused**? Free projects pause after about a week of inactivity -> click **Restore project**. Also check https://status.supabase.com and https://www.vercel-status.com.
5. GitHub Actions: did the last "Deploy database migrations" fail half-way? Look at its log.
6. If a database problem looks like data loss: stop changing things and go to section 5.
7. After recovery, write down what happened and why (a few lines are enough).

## 8. Sentry (error tracking)

Sentry collects crashes from the browser and the server and emails you. Docs checked 2026-10-28: https://docs.sentry.io/platforms/javascript/guides/nextjs/manual-setup/ and https://docs.sentry.io/platforms/javascript/guides/nextjs/configuration/build/. Setup steps are in `docs/hosting-setup.md` section 6b.

**What it does and does not do**
- Switched on only when `NEXT_PUBLIC_SENTRY_DSN` is set. Without it the app runs normally and sends nothing.
- Environment = `VERCEL_ENV` (`production` / `preview`, else `development`); release = `VERCEL_GIT_COMMIT_SHA`, so every error shows which deploy caused it.
- Privacy: no session replay, no profiling, no performance tracing (`tracesSampleRate` 0), `sendDefaultPii` off. Before sending, `src/lib/sentry-scrub.ts` removes email addresses, tokens (`token_hash`, `code`, `access_token`, `password`, `apikey`, `Authorization`, cookies) from messages, URLs, query strings, breadcrumbs and request data. At most the Supabase user id is attached (we do not set one at all today). Use an EU-region organisation (de.sentry.io) so the data stays in the EU.
- Handled errors that our code writes with `logEvent()` (table `app_events`) are not sent to Sentry; Sentry only sees unhandled errors. So nothing is reported twice. Do not add Sentry's `captureConsole` integration.
- Source maps (readable stack traces) are uploaded during the Vercel build only if `SENTRY_AUTH_TOKEN` is set, and deleted from the build output afterwards, so they are never public.
- No tunnel route (ad-blocker workaround): a few blocked browsers would not report errors, which is acceptable for a family app, and the tunnel would add a route that needs excluding from the middleware and uses function invocations. If it ever matters, add `tunnelRoute: "/api/monitoring"` to `withSentryConfig` in `next.config.ts` (`/api` is already excluded from the middleware matcher).

**Test that it works**
1. Vercel -> Settings -> Environment Variables: add `SENTRY_TEST_ENABLED` = `true` (Preview only is safest), redeploy.
2. Open `https://<preview-url>/api/debug/sentry-test`. You get a 500 error page; that is intended.
3. In Sentry -> Issues, the error "Sentry test error (intentional...)" appears within a minute, with environment and release set and readable file names/lines (if source maps are configured).
4. Delete `SENTRY_TEST_ENABLED` again and redeploy. Without it the URL returns 404.

**When a Sentry alert email arrives**
1. Open the issue: check environment, release (commit), and how many users/events.
2. If it started with the latest deploy and is serious -> Instant Rollback (section 2).
3. Otherwise fix on a branch; mark the issue "Resolved in next release".
4. If an issue contains an email or token that the scrubber missed: delete the event in Sentry (Issue -> Delete), then extend `src/lib/sentry-scrub.ts` and its test.

**Rotating `SENTRY_AUTH_TOKEN`:** Sentry -> Settings -> Developer Settings -> Organization Tokens: create a new token, update it in Vercel, redeploy, then revoke the old one.

### AeroDataBox quota

Basic plan: 400 units/month (routes 6, FIDS 2, flight dates 2). Every call is logged in `api_calls` (provider `aerodatabox`, column `units`, including charged failures: HTTP errors, schema-invalid 200s and timeouts at nominal cost). Check usage with `select sum(units) from api_calls where provider='aerodatabox' and created_at >= date_trunc('month', now())` (and per day with `date_trunc('day', ...)`).

The guard (`src/lib/server/flights-quota.ts`) reads those sums before each call. Knobs: `AERODATABOX_DAILY_UNITS` (daily cap) and `AERODATABOX_MIN_REMAINING` (monthly margin kept free, default 40).

Accepted risk: there are no reservations, so parallel instances can each pass the check and overshoot the daily cap by a few calls. The monthly margin of 40 units absorbs this. Raise `AERODATABOX_MIN_REMAINING` if it ever bites.

Nearby days ("±1 day" button in the flights panel, spec phase 4 section 12): each click spends up to 8 units (one airport, day −1 and +1, am+pm) through the same guard and cache keys (`fids_departures`); cached days are free. In `api_calls` they appear as `fids_departures` rows like the automatic lookup. If the monthly quota gets tight, the knobs above (`AERODATABOX_DAILY_UNITS`, `AERODATABOX_MIN_REMAINING`) also limit these checks; to switch the feature off, hide the button via `canCheckNearby` in `src/components/facts/flights-nearby.tsx`.

### OpenRouteService quota

Free Standard key: about 500 matrix requests per day. One plan generation makes at most one request (`src/lib/server/facts/drive-times.ts`), cached 90 days per destination point and place set. Every request is logged in `api_calls` (provider `openrouteservice`). The guard counts today's non-hit rows (Europe/Berlin day) before each request and refuses at `ORS_DAILY_REQUESTS` (default 400); it fails closed. When it refuses or ORS is down, plans generate without drive times. Check usage with `select count(*) from api_calls where provider='openrouteservice' and cache <> 'hit' and created_at >= date_trunc('day', now())`.

### Geoapify quota

Free plan: 3,000 credits per day, one credit per started block of 20 places. One interest lookup costs 1-5 credits (city sights: up to 15, three requests), cached 30 days per interest and destination point (`src/lib/server/facts/places.ts`). Every lookup is logged in `api_calls` (provider `geoapify`, credits in `units`). The guard sums today's credits (Europe/Berlin day) and refuses when they plus a headroom of 60 credits (one plan's parallel lookups at their maximum) would pass `GEOAPIFY_DAILY_CREDITS` (default 2,000, admin page); it fails closed. When it refuses, the key is missing or Geoapify is down, places come from Overpass (slow, but the plan still gets concrete places). Usage today: admin page, API section, or `select coalesce(sum(units),0) from api_calls where provider='geoapify' and created_at >= date_trunc('day', now())`.

## 9. Admin page

It never shows names, notes, purposes, plans or user ids. Anyone who is not an admin gets the normal 404 page. An "Admin" link appears in the header for admins only. The role lives in `profiles.role` and users cannot change it (no column grant), so it is set by SQL as the project owner:

1. Sign in once with your email so your profile exists.
2. Supabase dashboard -> **SQL Editor** -> **New query**, paste, replace the email, click **Run**:

```sql
update public.profiles set role = 'admin'
where id = (select id from auth.users where email = 'you@example.com');
```

3. It should say "Success. 1 row affected" (0 rows = wrong email or you never signed in). Reload the app; the **Admin** link appears.
4. Revoke the same way with `role = 'user'`. The demo account can never be admin (database check).

## 10. Budget alerts and Supabase keep-alive

A Vercel Cron job calls `GET /api/cron/budget-check` once a day (`vercel.json`, 20:30 UTC = 21:30/22:30 Berlin, late in the day so the daily numbers are nearly complete; Hobby plans run crons with up to one hour of jitter).

**What triggers an alert** (thresholds in `src/lib/server/admin/budget.ts`, caps from env):

| Kind | Condition | Level |
|---|---|---|
| `ai_daily` | AI spend today >= 80 % of `AI_GLOBAL_DAILY_USD` (error at 100 %) | warn / error |
| `ai_monthly` | AI spend this month >= 80 % of `AI_MONTHLY_ALERT_USD` (default 10; error at 100 %) | warn / error |
| `aerodatabox_monthly` | units remaining (last value reported by RapidAPI) < 2 x `AERODATABOX_MIN_REMAINING` (error below 1 x) | warn / error |
| `ors_daily` | ORS requests today >= 80 % of `ORS_DAILY_REQUESTS` (error at 100 %) | warn / error |
| `errors_24h` | more than `ALERT_ERRORS_24H` (default 20) `app_events` with level error in the last 24 h (error above 2 x) | warn / error |

**Delivery** (no new account needed): each alert is written to `app_events` as `budget.alert` (level warn/error, shown on the admin page under "Recent warnings and errors") and sent to Sentry with `captureMessage` (level warning, tags `budget_alert=true`, `alert_kind=<kind>`, `alert_level`). The Sentry fingerprint contains the date, so each day is a new issue and a "new issue" alert rule fires again every day. At most one alert per kind per Berlin day (the check looks for an existing `budget.alert` event of that kind today). Without `NEXT_PUBLIC_SENTRY_DSN` only the `app_events` row is written.

**Keep-alive:** the nightly backup (`backup.yml`) connects with `pg_dump`, but Supabase does not document that as "activity" for the 7-day pause rule. The UptimeRobot ping of `/api/health` does call the DB, but it is an external service that may not be set up yet. So the daily cron itself reads from the database (spend sums, `api_calls`, `app_events`) and writes a `cron.budget_check` event every run. The admin page shows the time of the last run under Health. If it says "Never run" or the time is more than a day old, the cron is not working.

### Setting up (Alex)

1. **CRON_SECRET:** generate a long random string (`openssl rand -base64 32`). Vercel -> project -> **Settings** -> **Environment Variables** -> add `CRON_SECRET` for **Production** (Preview not needed; crons only run on production). Redeploy. Vercel then sends `Authorization: Bearer <CRON_SECRET>` on every cron call, and the route answers 401 to anything else (also when the variable is missing). Save the value in your password manager.
2. **Check the cron:** Vercel -> project -> **Settings** -> **Cron Jobs** should list `/api/cron/budget-check`. Click **Run** to trigger it once. In Supabase -> Table editor -> `app_events` there is a `cron.budget_check` row. Or look at the admin page Health tile "Last budget check".
3. **Sentry alert rule** (needed once, so the alerts reach your inbox): Sentry -> **Alerts** -> **Create Alert** -> **Issues** -> choose project -> Set conditions: **When** "A new issue is created", **If** "The event's tags match" `budget_alert` `equals` `true` -> **Then** "Send a notification to" Member "Alex" (or the team; see the spam note in `docs/architecture.md`) -> name it "Budget alerts" -> **Save Rule**. Use "Test Rule" to see what it would send.
4. **Change thresholds:** edit the env vars in Vercel (Production) and redeploy: `AI_GLOBAL_DAILY_USD`, `AI_MONTHLY_ALERT_USD`, `AERODATABOX_MIN_REMAINING`, `ORS_DAILY_REQUESTS`, `ALERT_ERRORS_24H`. The admin page reads the same variables, so its bars match what the cron checks. The 80 % warning level is a constant (`WARN_AT` in `budget.ts`).
5. Also keep the hard spend limit in the Anthropic console; the app budget is a guard, not a billing limit.

### When an alert arrives

- `ai_daily` / `ai_monthly`: admin page -> AI cost -> by task. Check for a loop or a burst from the demo account (Users -> Demo account). Lower `AI_DEMO_DAILY_USD` or set `AI_ENABLED` unset to stop generation.
- `aerodatabox_monthly`: no new flight lookups are made below the margin (the guard refuses). Wait for the monthly reset or raise the plan.
- `ors_daily`: plans simply generate without drive times until the next Berlin day.
- `errors_24h`: admin page -> Recent warnings and errors, then Vercel logs for the route.

## 11. Inviting people and the email sender

Signup is invite-only (`signup_allowlist`). Admin page -> **Einladen / Invite**: enter an address and press the button. The server adds the address to the allowlist and sends Supabase's invite email (`auth.admin.inviteUserByEmail`) with a link into the app. The list below shows each address as **Offen / Pending** (never signed in) or **Angenommen / Accepted**, with **Widerrufen / Revoke** for pending ones (removes the allowlist row and the never-used account). Details: `docs/specs/phase-6-hardening.md` section 5.

### It works with either sender, but the built-in one is weak

- **Supabase's built-in sender** (default): only a few emails per hour for the whole project, often lands in spam, and the templates cannot be edited. Inviting still works: if the mail does not go out, the page says so and the address stays on the list, so the person can open the login page and request a normal sign-in link themselves. If the invite email does arrive, its link confirms the account and lands on the login page with a hint ("Einladung bestätigt ..."); the person then enters the address and gets a sign-in link. One extra step, nothing breaks.
- **Your own SMTP sender** (recommended before inviting family): higher limits, better delivery, and you can edit the email templates, which makes the invite link sign the person in directly and work on any device.

### Alex: set up a custom SMTP sender (one-off, ~20 minutes)

Candidates (free tiers change; **verify the current limits on the provider's pricing page before choosing**):
- **Resend** - about 3,000 emails/month and 100/day on the free plan (verify). Needs a domain you own (add the SPF/DKIM DNS records Resend shows).
- **Brevo** - about 300 emails/day free (verify). Works with a verified single sender address; a domain is better for delivery.
- **Postmark** - small free developer allowance (about 100/month, verify), very good delivery, needs a sender signature or domain.

Steps (Supabase dashboard; menu names move occasionally, search for "SMTP" if they differ):
1. At the provider: create an account, verify the sender domain or address, create SMTP credentials (host, port, username, password; for Resend the username is `resend` and the password an API key).
2. Supabase -> your project -> **Authentication** -> **Emails** -> **SMTP Settings** -> turn on **Enable Custom SMTP**.
3. Fill **Sender email** (an address on the verified domain, e.g. `noreply@yourdomain`), **Sender name** (`Travel Planner`), **Host**, **Port** (587 or 465 as the provider says), **Username**, **Password**. **Save**.
4. **Authentication** -> **Rate Limits**: raise "Rate limit for sending emails" to something sensible for your volume (the default with custom SMTP is low; verify the value shown).
5. **Authentication** -> **Emails** -> **Templates** (editable now):
   - **Magic Link** and **Confirm signup**: as in `docs/specs/phase-1-dashboard-steps.md` section 4.
   - **Invite user**: Subject `Einladung zu Travel Planner / Invitation to Travel Planner`, body:

```html
<h2>Travel Planner</h2>
<p>Du wurdest eingeladen. / You have been invited.</p>
<p><a href="{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=invite">Annehmen / Accept</a></p>
<p>Der Link ist nur kurz gueltig. / The link is valid for a short time only.</p>
```
   `{{ .RedirectTo }}` is `https://<host>/auth/confirm?locale=de|en&invited=1`, the same shape as the magic-link template, so the link works on any device and signs the person straight in.
6. Test: invite one of your own other addresses from the admin page, open the mail on your phone, check it is not in spam. If it is in spam: add SPF/DKIM/DMARC records at your DNS provider as the sender shows.
7. Tick it off in `docs/architecture.md` (backlog "Custom SMTP sender") and `docs/specs/phase-1-dashboard-steps.md` step 7.

### Common problems

- "Added to the list, but the email could not be sent": the hourly mail limit (built-in sender) or an SMTP error. Wait, or tell the person to use the login page.
- "This address already has an account": the person exists; nothing to do.
- Revoked by mistake: invite again. A person who already signed in cannot be revoked here (their account stays); remove them by deleting the account (Settings -> delete account for themselves, or Dashboard -> Authentication -> Users).

## 12. Runtime settings (admin page "Einstellungen")

The switches and limits that used to need a Vercel env var change and a redeploy are editable on the admin page: AI plans on/off, demo access on/off, the five AI budgets (`AI_USER_DAILY_USD`, `AI_ADMIN_DAILY_USD`, `AI_DEMO_DAILY_USD`, `AI_GLOBAL_DAILY_USD`, `AI_MONTHLY_ALERT_USD`), `AERODATABOX_DAILY_UNITS`, `AERODATABOX_MIN_REMAINING`, `ORS_DAILY_REQUESTS`, `GEOAPIFY_DAILY_CREDITS` and `ALERT_ERRORS_24H`. Secrets (API keys, `CRON_SECRET`, Supabase keys, `DEMO_PASSWORD`) are not settings and never appear there. Spec: `docs/specs/phase-6-hardening.md` section 6.

- **Precedence:** admin value, else the environment variable, else the code default. The environment variables are therefore now the *defaults*; keep them as they are or remove them. Each row shows the effective value and its source (Admin / Umgebungsvariable / Standard).
- **Zurücksetzen** deletes the admin value, so the environment variable or default applies again.
- **Emergency off stays in Vercel:** `AI_ENABLED=false` or `DEMO_ENABLED=false` in the Vercel environment cannot be overridden from the admin page; the row then shows "Per Umgebungsvariable gesperrt" and the toggle is disabled. To switch AI or the demo off even if the admin page or database is unavailable, set the variable to `false` and redeploy. (Unset or any other value does not lock: then the admin value decides, default off.)
- **Timing:** a save takes effect at once on the instance that handled it; other instances re-read within 30 seconds. After the first deploy of this feature the switches start from the env values.
- **If the settings table cannot be read** the app uses the environment variables and defaults (finite budgets, never unlimited) and tries again after a few seconds. The migration `20261102120026_app_settings.sql` must be applied (merge to `main`, **Deploy database migrations** green) before values can be saved; until then the page shows the env values and saving fails with a friendly error.
- **Audit:** every change writes an `app_events` row `settings.changed` (key, old value, new value, no user shown on the page). The last 20 are listed under the settings.

## 13. E2E tests (Playwright)

Browser tests for the main flows on a 360 px phone (`mobile`) and a 1280 px desktop (`desktop`). They run in CI (job `e2e` in `.github/workflows/ci.yml`) against a throwaway local Supabase and the production build. No secrets, no external API calls, no AI calls. Design and decisions: `docs/specs/phase-6-e2e.md`.

**Run locally (needs Docker; Alex's Mac has none, so CI is the normal place):**

```bash
supabase start -x studio,imgproxy,mailpit,edge-runtime,logflare,vector,realtime,storage-api,postgres-meta,supavisor
set -a; eval "$(scripts/e2e/env.sh)"; set +a      # local URL + demo keys only
npx playwright install chromium                    # once
npm run build                                      # NEXT_PUBLIC_* values are baked in at build time
npm run e2e                                        # starts `next start` with the provider stub itself
supabase stop --no-backup
```

Handy: `npx playwright test e2e/share.spec.ts --project=mobile`, `--ui`, `PW_CHANNEL=chrome` (use an installed Chrome). The setup refuses to run unless `NEXT_PUBLIC_SUPABASE_URL` is `127.0.0.1` or `localhost`, so it can never touch the hosted project. Do not export values from `.env.local` into the shell before running it.

**When a CI run fails:** open the run in GitHub -> **e2e** job. Failures show as annotations and in the log. Download the artifact `playwright-report` (HTML report, screenshots and traces) and open a trace with `npx playwright show-trace trace.zip`. A failure of `a11y.spec.ts` lists the axe rule and the element.

**Adding a flow:** add `e2e/<name>.spec.ts`, import `test`/`expect` from `./lib/fixtures` (gives `seed`, `anonContext`, `contextAs`). Anything that needs an external fact must be in the stub (`e2e/stub-fetch.cjs`) or must be shown as "unavailable" in the test.
