# ADR 0010: Sharing trips and purposes between users

Status: accepted (Alex, 2026-11-04, including his answers to the open questions: no notification email, PDF for read access too, shared purposes in "Find destinations", transitive purpose visibility accepted, shares of a disabled owner hidden, CLAUDE.md rule 6 amended). Decisions 1, 2 and 10 tightened after the review of PR #123 (2026-11-04) · Date: 2026-11-04 · Spec: `docs/specs/sharing.md` (decisions D1 to D26) · Issue #82

## Context
Until now every user table is private to its owner (ground rule 6); the only way to show a plan to someone else is a public, read-only share link (ADR 0005). Families and friends plan together, so Alex wants to share a trip or a trip purpose with another account, live, read-only or read/write. Alex decided the scope (trips with plan, versions and items; purposes; groups later), the two levels, what write allows, that the recipient sees the full travel group, that AI costs go to the acting user, leaving, the email lookup with its enumeration side effect, the admin user list, that the demo account is out, and that no notification is sent. The app is invite-only and small (family and friends). RLS policies are plain `owner_id = auth.uid()`, child tables use composite same-owner FKs, and the publishable key with RLS is used for everything done on behalf of a user (ADR 0001).

## Decision
1. **Live access through two access tables, `trip_shares` and `purpose_shares`** (owner, grantee, `read | write`, unique per resource and grantee, no self-share). Real FKs cascade when the resource or either user is deleted; a polymorphic table could not have them. **Grants are written only by `public.share_resource`**, a `security definer` function that only `service_role` may execute. The server action authorizes the session (owner, not demo, email lookup with its limits, admin-only user list), then calls it with the secret key. The function checks everything again: the owner owns the resource and is neither demo nor disabled, the grantee can receive shares, no self-share, and the cap of 10. Clients have no insert or update privilege on the share tables, so a known user id cannot be used to skip the server's rules. Unshare and leave stay direct deletes under RLS, because removing access needs no limit.
2. **RLS is widened by extra permissive policies, the owner policies stay.** Policies call `security definer` helpers in `private` that return id arrays (`shared_trip_ids()`, `writable_trip_ids()`, and the same for plans, groups and purposes), evaluated once per statement. The helpers read the share tables as definer, so there is no policy recursion. Groups and entries become readable only through a trip shared with you, never as a list. **A disabled owner is hidden on every recipient path** (Alex) through one helper, `private.is_active()`: share rows, trips and everything under them, purposes (also when reached through someone else's trip), names and emails in `share_contacts()`, and purpose references for new rows.
3. **Owner-only columns are guarded by a trigger, not by column grants.** Owner and grantee share the `authenticated` role, so grants cannot tell them apart. A trigger rejects changes to `group_id`, `group_text`, `group_structure` and `purpose_id` by anyone but the owner. Deleting, sharing and share links stay owner-only through the existing policies. Read access includes the PDF (Alex).
4. **Rows a grantee writes belong to the owner.** A `before insert` trigger copies `owner_id` from the parent trip or plan, so composite FKs, the version trigger and every owner-based query keep working. `plans.busy_by` and `plan_versions.created_by` record who acted. Pruning old versions goes through a definer function, so a write grantee cannot delete history directly.
5. **The plan always uses the owner's context.** A write grantee's run uses the owner's birthdate (for "me" and "my age" entries), home airports and plan language, read on the server with the secret key after RLS proved access. The same input gives the same hash and the same language whoever starts the run. Costs, budgets and rate limits are the actor's (Alex).
6. **A shared purpose can be used for the recipient's own trips and destination searches** (searches: Alex). On `trips` and `destination_searches` the purpose FK becomes a plain FK plus one trigger that allows the row owner's own purposes and purposes shared with the row owner. Unshare or leave clears the reference; a search keeps its label and cards, as after a purpose delete. Tags are read from the owner's purpose; only an untagged purpose gets the existing once-per-purpose Haiku call, charged to the searcher and stored on the purpose. Search lists stay owner-only and their cache hash stays per owner, so no list crosses users. A purpose seen only through a shared trip has access `read` and cannot be picked.
7. **Recipients are found by email with a durable limit; admins pick from a list** (Alex). 20 lookups per user per Berlin day, counted from `app_events`, plus a short in-memory limit. Demo and disabled accounts answer like unknown emails.
8. **No notification** (Alex). The recipient sees the share in "Shared with me". This keeps the app free of a second mail path: Supabase Auth can only mail invites and login links, so a notice would have needed a new provider API and secret.
9. **Concurrency: keep what exists, add one check.** The per-plan lock and `baseVersion` conflicts already cover two plan editors. Trip and purpose forms add an optimistic `updated_at` check. Items and open-item ticks are last write wins.
10. **The cap is atomic.** `share_resource` locks the resource row (`for no key update`), resolves an existing grant first (so a level change works at 10 grantees), then counts and inserts under the lock, so parallel calls cannot exceed 10.
11. **The migration ships alone, before the server code.** Without share rows the widened policies add nothing, and after decision 1 no client can create one. The owner filters and access checks in the server code ship in the same deploy as the share action.

## Consequences
- **Privacy: a shared trip shows the whole travel group, with names and birthdates of people who did not agree to it** (Alex's choice over a summary). The share box tells the owner this every time, before the button. The owner's own profile birthdate is not shown; the "me" entry shows the owner's name and age.
- **Account enumeration:** any user can learn whether an email has an account, up to 20 times a day. Accepted by Alex for an invite-only app; misses are counted on the admin page.
- A purpose shared with B and used on B's trip is visible to whoever B shares that trip with, because the plan needs it (accepted by Alex). The purpose share box says so.
- Recipients learn about a share only when they open the app.
- `share_resource` runs with the secret key and is the security boundary for grants; each of its checks has a pgTAP case, and a two-session test covers the cap under concurrency.
- A direct delete through the Data API removes a share without the server's event; events are analytics, so this is accepted.
- Five existing queries that meant "all rows I can see" must now filter by `owner_id` (trips, trip count, purposes, groups, busy plans). A missed filter shows a shared item in the wrong list; tests and review check each one.
- `destination_searches` and `trips` lose their same-owner purpose FK in favour of a trigger; the trigger is covered by pgTAP for owner, both share levels, a trip-only view, a disabled owner and a stranger.
- Plan versions written by a grantee stay with the owner's plan when the grantee's account is deleted (`created_by` becomes null).
- CLAUDE.md ground rule 6 carries the exception (spec section 7).
- Groups stay unshared. Sharing them later needs a way to link a hand-entered member to the account of the person it describes, which cannot be inferred from a name (spec section 10).
- One additive migration; the current app keeps working until the server PR adds the owner filters together with the first share action.
- UI (spec section 4): pages read `access` (`owner | write | read`) from the loaders and hide what the server would refuse anyway; the server stays the only enforcement. A recipient never receives the owner's birthdate, only the owner's age on the travel date, so the trip page feeds the group resolution a stand-in birthdate that yields exactly that age (`birthdateForAge`). Shared purposes are offered in the trip form and in "Find destinations" in their own option group labelled with the owner.
