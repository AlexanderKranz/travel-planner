# In-app feedback to GitHub issues (issue #83)

Status: accepted (Alex, 2026-11-02). Migration `20261108120033_feedback.sql` and the server part are implemented; the UI is a separate change. Decisions are numbered **[D#]**. ADR: `docs/adr/0008-feedback-to-issues.md`.

## What it is

A "Feedback" page, `/[locale]/app/feedback`. A signed-in user picks **Bug** or **Idea**, writes a text and can
attach one screenshot. Code adds the page they came from, the app version and a short browser label. The server
saves the report, removes emails and phone numbers from the text, and then **automatically** creates a public GitHub
issue with Alex's token. The issue carries the labels `bug` or `enhancement` plus `reported-by-user`, and an opaque
reference instead of the user's name. Screenshots stay private. Below the form, users see a list of their own
reports. Alex triages on GitHub; his `claude` label starts the Claude Code action. Users need no GitHub login. No LLM
calls.

## Decisions

- **[D1] Save first, then create the issue automatically.** There is no review step before the issue (Alex).
  - Every report is written to `feedback` with status `pending`, and then the server tries to create the issue.
  - Saving first means a GitHub outage, a rate limit or an expired token loses nothing. The row stays `pending` and
    the daily cron retries it ([D6]).
  - The user always gets "Received, reference FB-…", whatever GitHub answers.
  - Because the text becomes public without review, [D5] cleans it in code and the form says plainly that it will be
    public ([D13]).
- **[D2] Each report gets an opaque reference, `FB-` plus 8 characters.**
  - Alphabet `abcdefghjkmnpqrstuvwxyz23456789`, generated by the server with `crypto.getRandomValues` and rejection
    sampling (about 40 bits). Example: `FB-k3x9p2qa`.
  - Unique constraint; the server retries once on a collision.
  - The reference appears in the issue **title** (`[FB-k3x9p2qa] …`) and in the body.
  - Only the admin lookup turns it into an email ([D3]). The auth uuid, the email and the display name never appear on
    GitHub. A per-report reference cannot link two issues of the same person publicly; a uuid could.
- **[D3] Narrow admin exception.** CLAUDE.md gets this line, added by the coordinator (final wording):
  > Exception: for a feedback reference (`FB-…`) the admin can look up the reporter's email and view that report's screenshot; nothing else of theirs.

  - There is no inbox and no editor: the report text is already public on GitHub.
  - The admin page shows aggregates plus a lookup field ([D14]). The admin never sees trips, groups, purposes or
    plans.
  - Precedent: the user-accounts section already shows emails.
- **[D4] Page, version and client are added by code.**
  - **Page.** The feedback link passes `?from=<path>` (`usePathname()`, without query or hash). The server keeps it
    only if it is a same-origin app path. It removes the locale and replaces uuid segments with `:id` and the share
    token with `:token` (example: `/de/app/trips/<uuid>/edit` becomes `/app/trips/:id/edit`). Only this form is
    stored and published.
  - **Version.** Set by the server, never by the client: `VERCEL_GIT_COMMIT_SHA`, first 7 characters, or `local`
    (as in `/api/health`).
  - **Client.** A coarse label derived by the server with a small regex, for example `Chrome 130 · Android · 360px`.
    The viewport width comes from the client and is clamped to 200..4000. The raw user agent is not stored.
- **[D5] The text is cleaned in code and stays inert on GitHub.**
  - At submission (`sanitizeFeedbackText`, pure):
    - Invisible characters are removed: zero-width characters, bidi controls and the Unicode tag block U+E0000 to
      U+E007F, which can hide instructions for the agent.
    - Email addresses become `[email removed]`.
    - Phone numbers become `[phone removed]`: sequences of 7 or more digits, with an optional `+` and spaces, dots,
      dashes or brackets in between. ISO dates (`2026-11-02`) and version-like numbers are not touched.
    - Share links (`/s/<token>`, with or without host) become `/s/[token removed]`. A share token is a credential.
    - Any uuid becomes `[id]`.
  - Only the cleaned text is stored, so the row never holds more than what will be published.
  - The body goes into a fenced `text` code block. The fence is longer than any run of backticks in the text. Inside
    the block nothing renders: no hidden HTML comments, no `@mention` notifications, no live links or images.
  - **Title:** `[FB-<ref>] Bug: ` or `[FB-<ref>] Idea: ` plus the cleaned text on one line,
    with the characters `@`, `<`, `>`, `#` and the backtick removed. Longer than 60 characters: cut at the last word
    boundary within 59 and followed by "…", so the text stays at 60 (a hard cut at 59 when no space is at position 30
    or later; all counted in characters).
  - Names, dates and places in prose cannot be detected reliably. The form asks users to leave them out ([D13]).
- **[D6] Delivery and retries.**
  - **Right after submission.** The route answers "received" at once. It then attempts the issue in `after()` (from
    `next/server`), unless today's app-wide ceiling is reached ([D7]).
  - **Lease.** An attempt first claims the row through the SQL function `feedback_claim(p_id, p_ceiling)` ([D7]). The
    lease is its own column, `lease_until`, separate from `next_attempt_at`: a retry back-off must not count against
    the ceiling, a live lease must. A successful claim sets `lease_until` and `next_attempt_at` to `now() + 10 min`
    and `attempts + 1`, filtered on `status = 'pending'`, `next_attempt_at <= now()`, no live lease and
    `attempts < 20`, and returns the row. A row that returns nothing (not due, leased, or ceiling reached) is skipped.
    This prevents the inline attempt and the cron from both creating an issue. **Every outcome clears
    `lease_until`** (success, back-off, failed); a stop caused by GitHub (rate limit, auth) also gives the attempt
    back (`attempts - 1`), because it is not the report's fault.
  - **Duplicate guard.** If `attempts > 1`, an earlier try may have succeeded without being recorded. Before creating,
    the server searches `repo:<repo> in:title "FB-<ref>"`. If an issue exists, the row is linked to it.
  - **Cron.** The existing daily cron (`/api/cron/budget-check`) processes due `pending` rows, oldest first. It takes
    at most `min(10, ceiling left today)` per run.
  - **Answers from GitHub:**

    | Answer | What happens |
    |---|---|
    | `201` | Status `created`; `issue_number`, `issue_url` and `issue_created_at` set; `body` set to null (the issue is now the copy). |
    | `403` / `429` with `retry-after`, or `x-ratelimit-remaining: 0` | Stop the run. `next_attempt_at` = the reset time (`retry-after` or `x-ratelimit-reset`). |
    | `401`, or `404` on the repo | Stop the run: token expired, revoked or wrong repo. Log `feedback.github_auth_failed` at level error. Rows stay `pending`. |
    | `422` | Status `failed`, permanent. `last_error` = `validation`. |
    | `5xx` or network error | `next_attempt_at = now() + 1 h`. |
    | 8th attempt fails | Status `failed`. |

  - **Budget alert.** The budget run raises a new alert kind, `feedback_delivery`, when an auth failure happened
    today or a `pending` row is older than 48 h. It goes through Sentry like the other kinds and is deduped once per
    day. This also reminds Alex of an expired token.
- **[D7] Limits. No captcha.**
  - **Both limits are atomic.** Counting and writing happen in one transaction under a Postgres advisory lock, so
    parallel requests, server instances or the cron cannot all see the same remaining capacity. Both functions are
    `security definer`, executable by `service_role` only, and called by the server after its own checks.
  - **Per user:** 10 reports per Berlin day (Alex). The server inserts through `feedback_submit(...)`: it takes
    `pg_advisory_xact_lock(hashtext('feedback:user:' || owner_id))`, counts the owner's rows since Berlin midnight and
    inserts only below the limit; otherwise it returns `limited` and inserts nothing. Signature: `feedback_submit(p_owner, p_ref, p_kind, p_body, p_page_path, p_app_version, p_client, p_locale, p_limit)` returning `(outcome, feedback_id)` with `outcome` = `created` or `limited`; a duplicate `ref` raises `unique_violation` (23505) and the server retries once with a new reference. If the call fails, the
    submission is refused (fails closed). Admin
    setting `feedback_user_daily` (env `FEEDBACK_USER_DAILY`, int 0..100, default 10). 0 hides the form behind a
    note.
  - **App-wide issue ceiling:** issues **created** per Berlin day (`status = 'created'` and `issue_created_at` since
    midnight) plus rows currently leased for an attempt. `feedback_claim(p_id, p_ceiling)` takes
    `pg_advisory_xact_lock(hashtext('feedback:issues'))` and grants the lease only below the ceiling, so concurrent
    attempts cannot overshoot it. `p_ceiling` is the resolved setting `feedback_daily_issues`, passed in by the server
    (0 or null leases nothing). "Currently leased" means `status = 'pending'` and `lease_until > now()`. The delivery
    clears the lease on every outcome; if the server dies mid-attempt it expires after 10 minutes. Admin setting `feedback_daily_issues` (env `FEEDBACK_DAILY_ISSUES`, int 0..500, default 30). Above it,
    reports are still saved as `pending` and become issues on a later day through the cron. 0 pauses issue creation.
    Users are never refused because of this ceiling.
  - **Burst guard:** `rateLimit("feedback:<uid>", 3, 60_000)` against double submits (in memory).
  - When the per-user limit is reached, the form shows "again tomorrow" and the server logs `feedback.rate_limited`.
- **[D8] The demo account cannot send feedback (Alex).**
  - **UI:** every entry point is hidden for `is_demo`: the nav pill, the settings card and the error-view link.
    The "my reports" list is hidden too. A direct visit to `/app/feedback` shows a note instead of the form
    (`feedback.demoNote`: "Feedback needs your own account") with a link back.
  - **API:** `POST /api/feedback` reads the profile and returns 403 `demo_forbidden` before any count, upload or
    insert.
  - **Database:** users have no insert grant ([D10]), so a direct PostgREST insert with the demo JWT fails.
- **[D9] Screenshots: optional, private, never on GitHub.**
  - **Bucket:** private Supabase Storage bucket `feedback-screenshots`, the first Storage use in the project. No
    policies for anon or authenticated, so only the secret key reads and writes. Bucket settings: `file_size_limit`
    2 MB, `allowed_mime_types` `image/jpeg`, `image/webp`, `image/png`. Path: `<owner_id>/<feedback_id>.<ext>`.
  - **Client:** downscales to at most 1600 px on the long edge and re-encodes as WebP, or JPEG as a fallback, on a
    canvas. This also strips EXIF data such as GPS position. It sends one multipart request to the route handler
    `POST /api/feedback`. A route handler avoids the 1 MB body limit of server actions; Vercel allows 4.5 MB.
  - **Server:** the session, demo and limit checks come first, so a refused request never touches Storage. Then it
    checks the magic bytes and the 2 MB maximum.
  - **Issue:** shows only "Screenshot: yes (private)".
  - **Admin:** sees the screenshot through the reference lookup as a signed URL valid for 5 minutes ([D14]).
- **[D10] Writes go through the server only.**
  - `feedback` has RLS with an owner select policy (ground rule 6). That covers the "my reports" list.
  - No insert, update or delete grant for `authenticated`. The server writes with the secret key after its checks, so
    the demo block and the limits live in one place.
  - Admin reads (lookup, aggregates) use the secret key only after `requireAdmin()` / `getAdminSession()`, like the
    phase 6 admin reads. There is no admin RLS policy.
- **[D11] Token, labels and interfaces to devops.**
  - **Token:** Alex's fine-grained personal access token, this repo only, Issues read and write, 1-year expiry. Env
    vars: `GITHUB_FEEDBACK_TOKEN` and `GITHUB_FEEDBACK_REPO` (`owner/name`). Both server-only, never `NEXT_PUBLIC_`.
    Without the token, reports stay `pending` and the form still works.
  - **Issues are authored by Alex.** Labels are set at creation: `bug` (Bug) or `enhancement` (Idea), plus
    `reported-by-user`. Alex has push rights, so GitHub should not drop the labels; check on the first test issue.
    The server **never** sets `claude`.
  - **Labels come from a hardcoded allowlist** (`bug` or `enhancement`, plus `reported-by-user`), never from user input.
    `claude` must never be sent, so an anonymous user cannot start the agent.
  - **Workflow interface (designed in the devops plan):**
    - The claude-code-action workflow starts only when Alex adds the label `claude`.
    - It runs on Alex's Claude Pro subscription through `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), stored
      in a protected GitHub environment.
    - Limits: Sonnet, at most 40 turns, 30 minutes.
    - It has no production secrets and never merges.
  - **Branch protection** (separate PR): 1 required approval plus CODEOWNERS, so every agent PR needs Alex's approval.
  - **Runbook:** a new section "Feedback token", covering rotation before expiry (calendar reminder 11 months after
    creation; GitHub also mails before expiry), the `feedback_delivery` alert, and how to retry or clear `pending`
    rows.
- **[D12] Entry points.**
  - App shell: a small "Feedback" pill at the end of the main nav, with `?from=` (title: the full "Report a problem or idea"). Alex (2026-11-04) moved it there from a footer link below the content; the nav wraps at 360 px.
  - Settings: a card ("Report a problem or suggest an idea").
  - `components/app/error-view.tsx`: "Report this problem", with Bug preselected.
  - All three are hidden for demo ([D8]). There is no entry point for signed-out visitors, the share page or login.
- **[D13] Form, notice and "my reports" (mobile first, a11y, i18n).**
  - **Layout:** one column at 360 px.
    - Bug/Idea as a radio group, default Bug.
    - Textarea, 10 to 4000 characters, with a live counter.
    - Optional screenshot (`accept="image/png,image/jpeg,image/webp"`) with a preview and a remove button.
  - **Notice above the form:** "Your text will be published in our public GitHub project, without your name. Email
    addresses and phone numbers are removed automatically. Please leave out names, dates and trip details.
    Screenshots stay private; only the operator can see them."
  - **Success:** "Received, reference FB-…". Shown whatever GitHub answers.
  - **Errors:** `invalid`, `rate_limited`, `demo_forbidden`, `too_large`, `bad_image`, `failed`. Each maps to a
    message in a `role="alert"` region. Touch targets are 44 px.
  - **My reports:** below the form, the user's own rows through RLS, newest first, at most 50. Each row shows the
    reference, type, date (formatted in the UI) and status:
    - `pending` → "Received"
    - `failed` → "Received"; Alex sees failures as an aggregate
    - `created` → "Published", with a link to the issue (`issue_url`)
  - **i18n:** namespaces `feedback` and `admin.feedback` in both locale files, with the same keys. The fixed parts of
    the issue template are English (the repo language). The user text stays in the user's language.
- **[D14] Admin: aggregates plus a reference lookup.** A "Feedback" section on `/app/admin`:
  - Issues created per Berlin day (14 days), the `pending` count, the `failed` count, and the last delivery error
    class with its time.
  - A lookup field takes `FB-…` and returns email, date, type, status, issue link and, if one exists, a screenshot
    signed URL (5 minutes). The report text is not shown: it is on GitHub, or still pending.
  - Every lookup is audited as `admin.feedback_lookup` (admin `user_id`, props `{ ref: "FB-…" }`): the opaque reference
    shows which report was opened, never the email or the screenshot. Not-found lookups are audited the same way.
  - Not found and an invalid format give the same answer.
- **[D15] Logging.**
  - `api_calls`: every GitHub call writes `provider='github'`, `endpoint` `issues_create` or `issues_search`,
    `cache='bypass'`, status, ok, latency and `error_code`. `user_id` is the reporter for the inline attempt and null
    for the cron.
  - `app_events`, metadata only:
    - `feedback.submitted` (props `kind`, `has_screenshot`)
    - `feedback.rate_limited` (warn)
    - `feedback.rejected` (warn; props `reason`)
    - `feedback.issue_created` (props `issue_number`)
    - `feedback.deferred` (ceiling reached)
    - `feedback.delivery_failed` (warn; props `status`)
    - `feedback.github_auth_failed` (error)
    - `admin.feedback_lookup`
  - Never logged: the text, emails, or the reference together with the user id (except the admin's own lookup
    audit). Sentry gets no text either.
- **[D16] Retention and account deletion.**
  - The daily cron deletes screenshots 90 days after submission, through the Storage API, and sets
    `screenshot_path = null`. It deletes `created` rows after 180 days and `pending`/`failed` rows after 365 days.
  - `deleteAccount` removes `feedback-screenshots/<uid>/` before deleting the user, because Storage objects do not
    cascade. Rows cascade through `owner_id`.
  - Published issues stay on GitHub. Once the row is gone, nothing in the issue leads back to the user.

## Data (for the migration; developers write the SQL)

`public.feedback`

| column | type | null | notes |
|---|---|---|---|
| id | uuid pk | no | `gen_random_uuid()` |
| ref | text unique | no | check `^FB-[a-hjkmnp-z2-9]{8}$`, set by the server |
| owner_id | uuid | no | `references auth.users on delete cascade` |
| kind | text | no | check in (`bug`, `idea`) |
| body | text | yes | cleaned text, length 1..4000; null after the issue is created |
| page_path | text | yes | length <= 300, normalised per [D4] |
| app_version | text | no | `^[0-9a-f]{7}$` or `local` |
| client | text | yes | length <= 80 |
| locale | text | no | in (`de`, `en`) |
| screenshot_path | text | yes | null after purge |
| status | text | no | default `pending`, in (`pending`, `created`, `failed`) |
| attempts | smallint | no | default 0, 0..20 |
| next_attempt_at | timestamptz | no | default `now()` |
| lease_until | timestamptz | yes | live lease taken by `feedback_claim`, cleared by every settled delivery outcome; after an unexpected error (no settle) it simply expires after 10 min, counting against the ceiling until then |
| last_error | text | yes | length <= 60 (a class such as `rate_limited`, not a GitHub message) |
| issue_number | integer | yes | |
| issue_url | text | yes | check `^https://github\.com/[^/]+/[^/]+/issues/[0-9]+$` |
| issue_created_at | timestamptz | yes | |
| created_at / updated_at | timestamptz | no | `now()`, `private.set_updated_at()` trigger |

Check: `status = 'created'` requires `issue_number`, `issue_url` and `issue_created_at`.

Indexes:
- `(owner_id, created_at desc)`: user limit and my reports
- `(next_attempt_at) where status = 'pending'`: cron
- `(issue_created_at) where status = 'created'`: ceiling and per-day aggregate
- `(status)`

RLS and grants:
- RLS on. Revoke all from anon, authenticated and public.
- `grant select` to authenticated, with the policy "owner select" `(select auth.uid()) = owner_id`.
- No other grants, and no admin policy ([D10]).

Bucket `feedback-screenshots`: private, size and type limits per [D9], no policies.

Settings: `feedback_user_daily` and `feedback_daily_issues` in `SETTING_DEFS` ([D7]).

Implementation notes (server part):
- The cron work lives in `src/lib/server/feedback/cron.ts` and runs inside `GET /api/cron/budget-check`, before the budget evaluation.
- Screenshot storage and removal: `src/lib/server/feedback/storage.ts`. `removeUserAccount` removes the user's folder first and refuses to delete the user if that fails.
- The route answers `{ ok: true, ref, screenshot: 'none' | 'saved' | 'failed' }`; a failed upload keeps the report.
- `feedback.deferred` is logged when a claim returns nothing (not due, leased or ceiling reached).

Code:
- `src/lib/domain/feedback.ts` (pure, Zod `FeedbackInput`):
  - `newFeedbackRef`
  - `normalizePagePath`
  - `sanitizeFeedbackText`
  - `fenceFor`
  - `issueTitle`
  - `issueBody`
  - `clientLabel`
- `src/lib/server/feedback/submit.ts`: checks, insert, upload.
- `src/lib/server/feedback/deliver.ts`: lease, ceiling, create or search, the answer table in [D6]. Shared by
  `after()` and the cron.
- `src/lib/server/admin/feedback.ts`: aggregates and lookup.
- `src/lib/integrations/github.ts`:
  - `createIssue` and `findIssueByRef`
  - Zod-checked responses (`number`, `html_url`)
  - rate-limit headers parsed
  - 10 s timeout
- `src/app/api/feedback/route.ts`.

**Version:** a1b2c3d

**Screenshot:** yes (private)

<cleaned user text>

## Tests

- Vitest, pure functions:
  - `sanitizeFeedbackText`: emails, phone formats, ISO dates and version numbers kept, share links with and without
    host, uuids, invisible and tag characters.
  - `fenceFor`: backtick runs, HTML comments stay inside the fence.
  - `issueTitle`: `@` and `#` removed, single line, at most 60 characters cut at a word boundary with "…".
  - `normalizePagePath`, `clientLabel`, `newFeedbackRef` (alphabet, length), and an `issueBody` snapshot with no
    email, uuid or name in it.
- Vitest, route:
  - 401 when signed out; 403 for demo with no count, upload or insert.
  - 429 at 10 per day; a failed count fails closed.
  - Bad magic bytes and more than 2 MB are rejected.
  - "received" even when GitHub fails.
- Vitest, delivery:
  - The lease prevents a double create; an existing issue is found by its reference.
  - The answer table in [D6] (201, 403/429 with reset, 401, 404, 422, 5xx, 8th attempt).
  - The ceiling defers rows; the cron batch size.
- Vitest, labels: the labels sent to GitHub are always `bug` or `enhancement` plus `reported-by-user`, whatever the form
  contains, and never `claude`.
  - `api_calls` rows are written.
- Vitest, admin and budget:
  - The lookup needs admin and audits with the `FB-…` reference only; aggregates contain no identifiers.
  - The `feedback_delivery` alert rules.
- pgTAP:
  - No insert, update or delete grant for authenticated.
  - The owner sees only their own rows.
  - The `ref`, `issue_url` and created-requires-issue checks.
  - `feedback_submit`: the 11th report of a day returns `limited`; only `service_role` may execute it.
  - `feedback_claim`: no lease at the ceiling; a row with a live `lease_until` counts against it, a back-off does not; only `service_role` may execute it.
- Integration (local Supabase): 12 parallel submits by one user leave exactly 10 rows; parallel claims never lease
  more rows than the ceiling allows.
- E2E (later): submit at 360 px and see the row in my reports; the demo user sees no link and gets the note on a
  direct visit.

## Setup (Alex, before the first deploy)

1. Create the labels `reported-by-user` and `claude` in the repo (`bug` and `enhancement` exist by default).
2. Create the fine-grained PAT (this repo, Issues read/write, 1 year). Set `GITHUB_FEEDBACK_TOKEN` and
   `GITHUB_FEEDBACK_REPO` in Vercel Production (Preview optional; then preview deployments create real issues too, runbook section 18). Set a calendar reminder for rotation.
3. Submit one test report. Check that the issue was created and that both labels are on it.

## Settled after review (Alex, 2026-11-02)

1. **Abuse in public.** The invite-only allowlist plus the per-user limit is enough. A user's first report is not held
   back.
2. **Removal requests.** "My reports" does not explain how to request removal. Alex handles such requests by hand.
3. **Failed reports.** A permanently `failed` report shows as "Received" to the user.
