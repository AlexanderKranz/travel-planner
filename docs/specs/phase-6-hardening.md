## 1. Rate-limit audit

- **[D1] What "sensible" means here.** Paths that spend money or a quota (LLM, AeroDataBox, Overpass) already had a limiter plus a DB-backed guard. The gaps were the unauthenticated auth actions (a script could burn the shared mail quota or guess codes), the trip and purpose writes that start background work against external APIs, and the public health endpoint, which touches the database. Plain CRUD on the user's own rows is bounded by caps and RLS and costs only free-tier storage, so no per-call limiter was added there.
- **[D2] The limiter stays in memory; no DB-backed limiter.** `rateLimit()` counts per server instance. On Vercel Fluid compute one instance serves many concurrent requests and stays warm between them, so the counters do work in practice, but a new instance (scale-out or cold start) starts at zero, so the effective limit is `limit x instances`. This is documented in the file header and here. A DB-backed counter would add a database round trip to every request on the hot paths and a table to maintain, for a family-and-friends app on free tiers. It is **not needed** because every expensive path has a second, persistent guard: AI generation (per-user, demo and global daily USD budgets from `ai_usage`, the busy lock, the kill switch), flights (quota guard from `api_calls`), ORS (daily request count), `api_cache` for everything else, and Supabase Auth's own DB-backed limits for mail and codes. Revisit if the app is opened to the public or the admin page shows a burst that the limiter did not stop (the `budget.alert` cron already watches AI, AeroDataBox, ORS and the error count).
- **[D3] Auth limits never depend on whether an address is invited.** Keys are the normalised input address and the client IP only, so the neutral "if this address is invited ..." answer stays neutral; a limited request answers `rate_limited` for invited and unknown addresses alike. The IP limit is skipped when no proxy header exists (local development). Limits per address are strict (3 sign-in mails per 10 minutes) because the built-in Supabase sender allows only a few mails per hour for the whole project and an attacker could otherwise lock everyone out.

## 2. Error states

Findings before this change: only `global-error.tsx` and the share page's `not-found.tsx` existed. A thrown error in any page (for example `unwrap()` after a failed action) therefore replaced the whole page, including the navigation, with the global fallback; a missing trip showed Next's unstyled English 404; slow pages showed nothing until done.

- **[D4] Boundaries.** `src/app/[locale]/error.tsx` (public pages) and `src/app/[locale]/app/error.tsx` (inside the shell: header and navigation stay) render `ErrorView` (`src/components/app/error-view.tsx`): friendly translated text (`errorPage.*`), a retry button (`reset()`), a link home, and the Next error digest as an opaque reference. The raw `error.message` is never rendered. `ErrorView` calls `Sentry.captureException(error)`, because errors caught by a boundary are not seen by the SDK otherwise; server render errors are additionally reported by `onRequestError` (already in `instrumentation.ts`) with the same digest, so they can be matched.
- **[D5] Not-found and loading.** `[locale]/not-found.tsx` and `[locale]/app/not-found.tsx` (localized, inside the shell for the app; also what non-admins see on the admin page and what a foreign trip id shows), `[locale]/[...rest]/page.tsx` (calls `notFound()` so unknown URLs get the localized page; documented next-intl pattern), (the `[locale]/app/loading.tsx` skeleton was removed again: it made not-found answer 200, see phase-6-e2e.md D11). The share page keeps its own single 404 (no oracle between unknown, expired and revoked).
- **[D6] Global error.** `global-error.tsx` existed and already reports to Sentry. It now has a retry button, `lang` markers for the German text, visible Atlas colours and the digest. Its text stays hardcoded bilingual (the i18n provider is not available there; documented in the file).
- **Typed errors.** Server actions return `ActionResult` with an `ActionError` code, never a thrown message. Components map the code through `ErrorBanner` (`errors.*` in de + en); new codes `forbidden`, `already_member`, `email_failed` were added to `ActionError`, to both message files and to the plan route's status map (it is a `Record<ActionError, number>`, so the compiler enforced it). Pages use `unwrap()`: `unauthenticated` redirects to login, `not_found`/`invalid` call `notFound()`, anything else throws into the new boundary.
- **External-API failures** were already handled: the facts panels, flights loader/nearby, places loader and the plan runner catch fetch failures and show the translated "unavailable" or "rate limited" state with a retry button and the source note. No change needed; verified by reading each loader.

## 5. Invite flow

- **[D10] The allowlist already exists; no migration.** `signup_allowlist` (phase 1) has admin-only RLS policies for select, insert and delete, the Before User Created hook and the fail-closed `handle_new_user` trigger. The invite action uses the admin's own session for those (RLS enforces the permission a second time) and the secret key only for the Auth admin API (`inviteUserByEmail`, listing last sign-ins, deleting a never-used account), which has no RLS equivalent. A new `invites` table would only duplicate the allowlist.
- **[D11] Flow.** `inviteUser` (`src/lib/server/admin/invites.ts`): admin check (`getAdminSession`, non-throwing variant of `requireAdmin`, so the action returns `forbidden` instead of a 404), Zod validation, rate limit (10 per admin per hour), allowlist insert (an existing row is fine, so "resend" works), then `inviteUserByEmail(email, { data: { locale }, redirectTo })`. Typed errors: `already_member` (Supabase says the user exists), `email_failed` (any other send failure, including the hourly limit), `rate_limited`, `forbidden`, `invalid`. Events are logged without any address (`admin.invite_sent`, `admin.invite_existing`, `admin.invite_mail_failed`, `admin.invite_revoked`).
- **[D12] Works with either sender.** The allowlist row is written before the mail, so if the mail fails (built-in sender limit, spam, SMTP error) the person can still request a normal sign-in link on the login page, and the admin is told exactly that. One redirect URL serves both templates: `redirectTo = <APP_URL>/auth/confirm?locale=<l>&invited=1`.
  - With the **custom "Invite user" template** (runbook section 11, same token-hash link shape as the magic-link template): `{{ .RedirectTo }}&token_hash=...&type=invite`; `/auth/confirm` accepts `type=invite` (added to `ConfirmQuery`) and signs the person in on any device.
  - With **Supabase's default template**: Supabase verifies the invite (the account becomes confirmed) and redirects with the session in the URL fragment, which a server route cannot read. `/auth/confirm` therefore sends `invited=1` without token to `/<locale>/login?invited=1`, which shows a friendly hint instead of the link-invalid error. The person types the address and signs in with the normal link.
- **[D13] Pending / accepted.** Derived, not stored: accepted = the Auth user has a `last_sign_in_at`; everything else is pending (including an allowlisted address with no account yet, and the owner's pre-seeded row until the first sign-in). `signup_allowlist.used_at` is not used for this, because the signup trigger sets it when the invite creates the (unconfirmed) account, not when it is accepted. The demo address is hidden from the list. Emails are shown (admin-only page, the admin typed them) and never logged.
- **[D14] Revoke.** Pending only. It deletes the never-used Auth user first (so the invite link dies), then the allowlist row; if deleting the account fails the row stays and the button can be retried. If the person signed in meanwhile, nothing is deleted and the admin gets `conflict` ("the account stays"). Accepted accounts are not revoked from this page (account deletion is a separate, deliberate action).
- **Tests.** `invites.test.ts` runs the actions against a mocked Auth admin client and a mocked session (no real email can be sent): admin-only (a non-admin never creates the admin client), validation, allowlist-first order and arguments, resend, existing account, mail failure keeps the row, rate limit on the 11th invite, no address in logs, pending/accepted derivation, demo address hidden, revoke paths (including the signed-in conflict and the delete failure). `route.test.ts` covers the confirm route for `type=invite` and the fragment fallback. pgTAP is unchanged: no schema change (the allowlist's policies are already covered in `supabase/tests/rls.test.sql`).

## 6. Runtime settings (admin page)

Request from Alex: change switches and limits without Vercel env vars and a redeploy.

- **[D16] Table.** `app_settings (key text pk, value jsonb, updated_at, updated_by)`, migration `20261102120026_app_settings.sql`. RLS on, no policies, no grants for anon/authenticated (only `service_role`), like `api_cache`; `value` must be a JSON boolean or number, so a secret string cannot be stored by accident. pgTAP: RLS on, no policies, no privileges for anon/authenticated (including an admin user session), type and key constraints.
- **[D17] Covered settings** (`src/lib/settings.ts`, each with a Zod schema, min, max): `ai_enabled`, `demo_enabled` (bool); `ai_user_daily_usd` (0-100), `ai_admin_daily_usd` (0-100), `ai_demo_daily_usd` (0-100), `ai_global_daily_usd` (0-1000), `ai_monthly_alert_usd` (0-10000), all with at most cents; `aerodatabox_daily_units` (int 0-1000), `aerodatabox_min_remaining` (int 0-100000), `ors_daily_requests` (int 0-5000), `alert_errors_24h` (int 0-10000). The save action accepts only these keys (a unit test asserts no secret-like variable is among them).
- **[D18] One helper, existing guards unchanged.** `src/lib/server/settings.ts`: `getSetting(key)`, `getAllSettings()` and `getEffectiveEnv()`, which returns `process.env` with the resolved values written over the 11 variables. Every place that read those variables already accepted an `env` argument (`isAiEnabled`, `userCapMicroUsd`, `globalCapMicroUsd`, `orsDailyCap`, `readBudgetConfig`, `isDemoEnabled`, `getDemoCredentials`, the AeroDataBox quota), so they now receive `await getEffectiveEnv()` and their parsing and tests are untouched. Call sites changed: `getBudgetStatus`, `plan-pipeline` (gate, budget, plan state), `group-text`, `warm`, `flights-quota`, `drive-times`, the login page and `signInDemo`, admin `stats` and the budget cron (`defaultBudgetDeps` is now async). `grep process.env` finds the 11 names only in `settings.ts`/`lib/settings.ts` and in the parsers that still receive the overlay.
- **[D19] Precedence and the hard off.** DB value > env > code default; an invalid DB value (wrong type, out of range) is ignored. For the two switches an environment value of exactly `false` (any case, trimmed) is a hard off: the resolver returns `locked`, the save action refuses without writing, the UI shows "Per Umgebungsvariable gesperrt" and a disabled control. Unset or other values do not lock. Note: this is a behaviour change for `AI_ENABLED=true` in env: the admin can now switch it off from the page.
- **[D20] Cache and failure.** Per-instance cache, 30 s TTL (`SETTINGS_TTL_MS`); saving or resetting invalidates the local cache, other instances catch up within 30 s (documented in the runbook and the admin page text). If the table cannot be read (missing migration, DB error, missing key) the helper logs to the console, uses env/defaults and retries after 5 s. Every setting has a finite default, so budget checks never become unlimited; the existing fail-closed behaviour of the budget read itself is unchanged.
- **[D21] Admin UI and actions.** `components/admin/settings-section.tsx` ("Einstellungen"): grouped rows with effective value, source pill (Admin / Umgebungsvariable / Standard), switch or number input with range hint, Save, "Zurücksetzen" (deletes the DB value) and the last 20 changes. Actions `saveSetting`, `resetSetting`, `listSettings` in `src/lib/server/admin/settings.ts` check the admin role first with `getAdminSession()` (the non-throwing form of `requireAdmin()`, as for invites, so actions return `forbidden` rather than a 404), are rate limited (20 changes per minute per admin), validate with Zod, then write with the secret key (the only way to the service-role table). The page itself calls `requireAdmin()`.
- **[D22] Audit.** Each save or reset logs `app_events` `settings.changed` with props `key`, `old`, `new` (+ `oldSource` or `reset`); numbers and booleans only. The page lists key, old, new and time, no user.
- **Tests.** `lib/settings.test.ts` (precedence, invalid DB/env values, hard off, schemas incl. edges, unknown and secret-like keys rejected, overlay), `server/settings.test.ts` (DB > env > default, hard off against a DB `true`, TTL, invalidation, read failure and thrown client fall back to finite defaults), `admin/settings.test.ts` (non-admin never reaches the secret-key client, validation, effect after save, audit payload, locked refusal, failed write not audited, rate limit, reset, recent changes without user ids). pgTAP as in D16.
